# Security Core

The security core is a transport-independent, standard-library-only policy core. It defensively copies provider/model inputs into immutable mapping proxies, accepts sensitivity only through a separate authenticated server-owned policy argument (not the caller request object), classifies missing, unknown, or non-string sensitivity as restricted, selects the smallest capable permitted local model, and never authorizes fallback. Confidential/restricted requests cannot select cloud. Internal requests prefer a capable local model, but may select an allowed cloud model only when no capable permitted local model exists and a valid single-request approval is verified.

When no local model can meet a public/internal request, a configured cloud model may be selected only with a valid HMAC approval. The canonical versioned envelope binds issuer, request ID, actor, task, required capability, preferred provider/model, caller-supplied canonical payload/content SHA-256, trusted sensitivity, selected provider/model, policy version, registry version, issue/expiry times, and nonce. Secrets must be at least 32 bytes; TTL and identifier/nonce sizes are bounded; expiry at or before verification time is rejected. Nonce consumption is lock-protected so one verifier instance permits exactly one concurrent consumer.

Replay state is deliberately single-process and in-memory. Multi-process or distributed deployment requires an atomic durable nonce store before promotion. Endpoint validation requires explicit hosts and ports, loopback IPs for local HTTP, HTTPS for cloud, and globally routable cloud IP literals. DNS resolution, rebinding defense, connection-time address pinning, redirects, and TLS policy are deferred to the future authenticated transport gate; hostname allowlisting alone is not represented as complete SSRF defense.

The audit event contains allowlisted routing metadata only. Actor identity and approval state are carried by the policy `Decision` and derived by the audit builder; callers cannot substitute either value at event construction. The audit builder generates its timestamp from a trusted, timezone-aware clock dependency and normalizes it to UTC; a naive clock result is rejected. The event has no prompt, message, retrieval-content, headers, token, endpoint, or secret field. It does not make network calls and does not implement an HTTP server or provider execution/fallback.

`config/example-registry.json` is illustrative and keeps cloud disabled. It is not automatically loaded or trusted.
